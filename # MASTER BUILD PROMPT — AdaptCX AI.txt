## 2. Core Mission Directive

Build **AdaptCX**, a multi-tenant SaaS platform that lets a business make its own website feel personally written for *whoever is visiting it*. A business defines the different "use cases" (types of businesses/customers) it serves and its baseline website copy. AI then generates a tailored content variant of that copy per use case. On a visitor's first visit, a short quiz asks "What best describes your business?" — once answered, the site instantly swaps its headline, subheadline, features, CTA, and testimonial to the AI-generated version written specifically for that use case, and remembers the choice for future visits.

This is a hackathon submission for the theme **"AI for Customer Experience."** The judged criteria are: problem-solution fit, real AI integration (not fake/hardcoded outputs), functional full-stack execution, and a working public deployment. Favor a smaller set of fully working, genuinely AI-driven features over a large set of shallow ones.

---

## 3. Product Goal

Most B2B websites show the exact same generic copy to every visitor, even though a "healthcare clinic" and a "fintech startup" landing on the same SaaS homepage care about completely different pain points. Businesses know this but can't realistically hand-write and maintain N different landing page versions. AdaptCX solves this by letting a business:

- Describe its product once and list the distinct use cases/industries it serves.
- Let AI generate a tailored version of every key content block for each use case.
- Ask visitors, once, which use case they belong to (via a lightweight quiz).
- Instantly render the matching tailored content, with zero manual copywriting per segment.
- See which use cases are visiting and converting best.

## 4. Mandatory Features

**Business (tenant) side:**
- Business signup/login (JWT auth, bcrypt password hashing).
- Onboarding: business name, product description, brand tone/voice description.
- **Use Case management**: CRUD for target use cases (e.g., "Healthcare," "E-commerce," "Fintech"), each with a short description of that use case's pain points/priorities.
- **Baseline Content Blocks**: define the default/generic version of: hero headline, hero subheadline, 3 feature bullets, CTA button text, and one testimonial.
- **AI Variant Generation**: one-click "Generate tailored content" — AI produces a full tailored set of all content blocks for every use case, editable before publishing.
- **Quiz Configuration**: customize the quiz question shown to visitors (default: "What best describes your business?"); options are auto-populated from the Use Cases list.
- **Live Preview**: a page that renders the site exactly as a visitor would see it, with a use-case switcher to preview every variant instantly.
- **Embeddable Widget**: a copyable `<script>` snippet + short instructions for embedding the quiz + dynamic content swap on an external website.
- **Insights Dashboard**: visits per use case, quiz completion rate, CTA-click rate per use case, and a chart comparing performance across use cases.

**Visitor-facing side:**
- A public demo landing page (`/site/:businessId`) that behaves like the business's real website: shows baseline content, then a quiz overlay/banner on first visit, then instantly re-renders with the tailored content for the selected use case, and skips the quiz on return visits (remembered via cookie/localStorage).

**Cross-cutting:**
- Full multi-tenant data isolation — one business must never see or affect another business's data.
- All AI calls happen server-side only; the API key is never exposed to the frontend.

## 7. User Flow

1. Business signs up → onboarding (product description + brand tone) → empty dashboard.
2. Business defines 2-5 use cases on `/use-cases` (e.g., "Healthcare," "Retail," "SaaS").
3. Business writes baseline content on `/content-blocks` (their current generic homepage copy).
4. Business clicks "Generate tailored content" on `/content-studio` → Claude produces a full tailored variant per use case → business reviews/edits/publishes.
5. Business customizes the quiz question (optional) and checks `/preview` to see each variant.
6. Business copies the embed snippet from `/widget-setup`, or simply shares the `/site/:businessId` demo link.
7. A visitor opens `/site/:businessId` → sees baseline content + quiz prompt → picks their business type → page instantly re-renders with the tailored variant → choice is stored (cookie/localStorage) so a return visit skips the quiz.
8. Business checks `/dashboard` to see which use cases are visiting most and converting best (CTA clicks), and iterates on content.

## 10. Database Schema (Production SQL for PostgreSQL)

```sql
-- Businesses (tenants)
CREATE TABLE businesses (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_name TEXT NOT NULL,
  email TEXT UNIQUE NOT NULL,
  password_hash TEXT NOT NULL,
  industry TEXT NOT NULL,
  product_description TEXT NOT NULL,
  brand_tone TEXT NOT NULL,
  quiz_question TEXT NOT NULL DEFAULT 'What best describes your business?',
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Target use cases (visitor business types) per business
CREATE TABLE use_cases (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  label TEXT NOT NULL,
  pain_points TEXT NOT NULL,
  sort_order INT DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Baseline content blocks per business
CREATE TABLE content_blocks (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  block_key TEXT NOT NULL CHECK (block_key IN ('hero_headline','hero_subheadline','feature_1','feature_2','feature_3','cta_text','testimonial')),
  default_value TEXT NOT NULL,
  UNIQUE(business_id, block_key)
);

-- AI-generated tailored variants, one row per (use_case, block_key)
CREATE TABLE content_variants (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  use_case_id UUID NOT NULL REFERENCES use_cases(id) ON DELETE CASCADE,
  block_key TEXT NOT NULL CHECK (block_key IN ('hero_headline','hero_subheadline','feature_1','feature_2','feature_3','cta_text','testimonial')),
  generated_value TEXT NOT NULL,
  is_published BOOLEAN DEFAULT TRUE,
  created_at TIMESTAMPTZ DEFAULT now(),
  UNIQUE(use_case_id, block_key)
);

-- Visitor sessions (tracks which use case a visitor selected)
CREATE TABLE visitor_sessions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  use_case_id UUID REFERENCES use_cases(id) ON DELETE SET NULL,
  session_token TEXT UNIQUE NOT NULL,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- Analytics events (views, CTA clicks) tied to a visitor session
CREATE TABLE events (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  business_id UUID NOT NULL REFERENCES businesses(id) ON DELETE CASCADE,
  use_case_id UUID REFERENCES use_cases(id) ON DELETE SET NULL,
  session_token TEXT NOT NULL,
  event_type TEXT NOT NULL CHECK (event_type IN ('page_view','quiz_shown','quiz_answered','cta_click')),
  created_at TIMESTAMPTZ DEFAULT now()
);

CREATE INDEX idx_use_cases_business ON use_cases(business_id);
CREATE INDEX idx_content_blocks_business ON content_blocks(business_id);
CREATE INDEX idx_content_variants_business ON content_variants(business_id);
CREATE INDEX idx_visitor_sessions_business ON visitor_sessions(business_id);
CREATE INDEX idx_events_business ON events(business_id);
CREATE INDEX idx_events_use_case ON events(use_case_id);
```

## 11. Row Level Security (RLS) / Data Isolation Rules

Since auth is handled by your own Express/JWT layer (not Supabase Auth), enforce tenant isolation **in application code**, not via Supabase RLS policies tied to `auth.uid()`. Rules:

1. Enable RLS on every table below, with a default-deny policy — only the backend's Supabase **service role key** (never exposed to the frontend) can bypass RLS and access data.
2. Every backend query touching `use_cases`, `content_blocks`, `content_variants`, `visitor_sessions`, or `events` **must** include a `WHERE business_id = :authenticatedBusinessId` clause, where `authenticatedBusinessId` comes from the verified JWT — never from a client-supplied parameter.
3. Implement a reusable Express middleware `requireAuth` that decodes and verifies the JWT and attaches `req.businessId`. All protected route handlers use `req.businessId`, never a value from `req.body`/`req.query`.
4. The public routes (`/site/:businessId` page and its supporting `/api/public/:businessId/*` endpoints) are the one exception: they only ever read published `use_cases`/`content_blocks`/`content_variants` and write `visitor_sessions`/`events`, all scoped strictly to the `:businessId` in the URL, and must never expose any other business's data or require the JWT.

```sql
ALTER TABLE use_cases ENABLE ROW LEVEL SECURITY;
ALTER TABLE content_blocks ENABLE ROW LEVEL SECURITY;
ALTER TABLE content_variants ENABLE ROW LEVEL SECURITY;
ALTER TABLE visitor_sessions ENABLE ROW LEVEL SECURITY;
ALTER TABLE events ENABLE ROW LEVEL SECURITY;
-- No permissive policies are created; only the service role (used exclusively by the backend) can bypass RLS and read/write.
```

## 12. Backend API Routes

**Auth**
- `POST /api/auth/signup` — body: business_name, email, password, industry, product_description, brand_tone. Hashes password, creates business, returns JWT.
- `POST /api/auth/login` — body: email, password. Returns JWT.
- `GET /api/auth/me` — returns current business profile (requireAuth).

**Use Cases**
- `GET /api/use-cases` (requireAuth)
- `POST /api/use-cases` (requireAuth)
- `PUT /api/use-cases/:id` (requireAuth)
- `DELETE /api/use-cases/:id` (requireAuth)

**Content Blocks**
- `GET /api/content-blocks` (requireAuth)
- `PUT /api/content-blocks/:block_key` — upsert baseline value (requireAuth)

**Content Studio (AI Variant Generation)**
- `POST /api/content-variants/generate` — generates a tailored variant of every content block for every use case (requireAuth).
- `GET /api/content-variants` — list all variants, grouped by use case (requireAuth).
- `PUT /api/content-variants/:id` — edit a generated value or toggle `is_published` (requireAuth).

**Quiz Config**
- `PUT /api/quiz-config` — update `quiz_question` (requireAuth).

**Public Site / Widget**
- `GET /api/public/:businessId/site` — returns business's `quiz_question`, ordered `use_cases` (id + label only), and current baseline `content_blocks`. No auth required.
- `POST /api/public/:businessId/select-use-case` — body: `use_case_id`, `session_token` (client-generated UUID, sent back on subsequent calls). Creates/updates the `visitor_sessions` row, logs a `quiz_answered` event, and returns the published `content_variants` for that use case (falling back to `content_blocks` defaults for any block missing a published variant).
- `POST /api/public/:businessId/event` — body: `session_token`, `event_type` (`page_view` | `quiz_shown` | `cta_click`), optional `use_case_id`. Logs the event. No auth required.

**Insights**
- `GET /api/insights/dashboard` — per-use-case counts of `page_view`, `quiz_answered`, and `cta_click` events, plus a computed CTA-click rate per use case (requireAuth).

## 13. AI SDK Setup & Server-Side Security

- Install `@anthropic-ai/sdk` in the backend only.
- Store the key as `ANTHROPIC_API_KEY` in the backend's `.env` — never in any frontend `.env`, never in any client-bundled code, never logged.
- Create a single shared module `backend/src/lib/anthropic.js` that exports a configured client and a `generateJSON(systemPrompt, userPrompt, schema)` helper that:
  1. Calls `claude-sonnet-4-6` with the given system + user prompt.
  2. Instructs the model (in the system prompt) to return **only valid JSON, no markdown fences, no preamble**.
  3. Parses the response with `JSON.parse`, defensively stripping ```` ```json ```` fences if present, and validates the result against a Zod schema before returning it.
  4. Throws a clear error (caught by the route handler and returned as a 502) if parsing/validation fails, rather than passing malformed data downstream.
- The only route that calls the AI is `POST /api/content-variants/generate`, and it is behind `requireAuth`.

## 18. Security Requirements

- Passwords hashed with bcrypt (salt rounds ≥ 10) — never stored or logged in plaintext.
- JWTs signed with a strong secret from env, short-to-medium expiry (e.g., 7 days), verified on every protected route via `requireAuth` middleware.
- `helmet` and `cors` (locked to the deployed frontend origin for authenticated routes; public routes allow cross-origin so the widget can be embedded on third-party sites) configured on the Express app.
- Rate-limit the public `POST /api/public/:businessId/select-use-case` and `POST /api/public/:businessId/event` routes (e.g., `express-rate-limit`, ~30 requests/minute/IP) since they require no auth.
- All Supabase access from the backend uses the **service role key**; this key must never be sent to or referenced by any frontend code.
- Validate that `use_case_id` values passed to any public endpoint actually belong to the `:businessId` in the URL before writing/reading — never trust a client-supplied ID pairing across tenants.

## 22. Acceptance Criteria

- A new business can sign up, log in, and reach an empty dashboard — no other business's data is ever visible to them.

- `/dashboard` shows real, computed (not fake) per-use-case visit/quiz-answer/CTA-click counts and rates.
- No API key, JWT secret, or Supabase service role key appears anywhere in frontend code, browser network responses, or git history.
- The full application builds and runs locally per the README, and is reachable at the deployed public URLs.
